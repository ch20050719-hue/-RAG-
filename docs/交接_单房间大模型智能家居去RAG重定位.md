# 项目交接：单房间智能家居项目去 RAG 重定位

> 状态：历史软件改造交接文档。本文中的代码修改指令不再执行；Python/RAG/Agent/后端/网页源码已移至 `F:\agrnt` 备份，当前项目只维护 STM32 固件与已确认硬件。当前有效范围以根目录 `agents.md`、`readme.md` 和最新项目交接说明为准。

> 用途：将本文档交给新的对话或开发助手，直接据此修改项目。本文档是独立交接上下文，不要求读取当前对话历史。

> 交接日期：2026-09-21

## 一、已经确定的项目方向

项目只做**单个房间**，不扩展多房间、多家庭、多租户场景。

项目论文不体现 RAG，项目定位统一改为：

> **大模型自然语言理解 + 固定工具调用 + 状态验证 + 安全控制**

建议项目名称：

> **基于大模型的单房间智能家居环境感知与安全控制系统**

最终系统链路：

~~~text
用户自然语言
    ↓
大模型自然语言理解
    ↓
结构化意图与参数
    ↓
固定设备工具调用
    ↓
设备注册/类型/在线状态/命令状态/过期时间校验
    ↓
安全规则校验
    ↓
模拟设备或 MQTT 适配器执行
    ↓
设备状态与执行回执
    ↓
向用户解释执行结果
~~~

大模型只负责理解用户表达、识别意图和提取参数；大模型不能直接访问 GPIO、任意 MQTT Topic 或底层数据点，也不能自行生成新的设备控制规则。

## 二、关于 RAG 的最终决策

### 决策

**移除运行时 RAG，不再把 RAG 作为项目核心能力，也不在论文中介绍 RAG。**

这里的“移除”优先指：

- 家居请求处理主链路不再执行向量检索；
- 不再依赖 Embedding、向量数据库、查询改写或动态知识召回来决定设备操作；
- 文档、README、项目介绍和论文方向不能再把项目描述成“RAG 智能家居控制平台”；
- 可以暂时保留通用 RAG 代码文件作为历史基座，前提是它们不再进入单房间家居业务默认运行路径。

### 为什么删除运行时 RAG

当前项目中的控制依据已经是确定性的：

- 房间数量固定为一个；
- 设备类型和设备能力固定；
- 控制入口是固定工具；
- 自动控制模式和场景规则是预先配置的；
- 设备执行前有注册、类型、在线、命令状态和 TTL 校验；
- 执行后有模拟回执或 MQTT 回执；
- 安全边界由程序规则控制，而不是由检索结果决定。

因此，RAG 对“开灯、关灯、开风扇、读取环境、控制水泵、门锁操作、模式切换”等核心流程没有明显增益，反而会增加检索延迟、依赖复杂度和不可控上下文。设备实时状态也应通过设备服务和固定工具读取，不能用知识库内容替代。

静态配置仍然保留，但它们不属于 RAG：

- knowledge_base.json：可作为固定配置或提示词素材；
- risk_rules.json：作为固定安全规则；
- 设备说明和场景说明：作为开发文档或固定提示词素材。

不要把“保留固定规则”误写成“继续使用 RAG”。

## 三、需要修改的核心代码

请先阅读实际代码和当前 Git 状态，再进行修改。不要直接删除整个 financial_rag 目录，也不要破坏已经存在的家居工具和安全校验。

### 1. 主编排链路

重点检查：

~~~text
financial_rag/rag_backend/app/multi_agent_system/orchestrator.py
~~~

当前需要处理的内容包括：

- AgentOrchestrator 中的 enable_rag 默认配置；
- 初始化 Embedding/Search/RAG 服务的逻辑；
- process_user_request() 中对 _retrieve_home_knowledge() 的调用；
- RAG 检索进度提示和 execution_path 中的 RAG 描述；
- 向 HomeSpecialist 传递但实际未被有效使用的 rag_context。

修改后，单房间家居请求应直接进入自然语言理解、固定工具调用和状态/安全验证链路。

### 2. 家居专家和固定工具

重点检查：

~~~text
financial_rag/rag_backend/app/multi_agent_system/agents/home_specialist.py
financial_rag/rag_backend/app/home_automation/device_tools.py
financial_rag/rag_backend/app/home_automation/device_service.py
financial_rag/rag_backend/app/home_automation/safety_rules.py
~~~

这些模块是新定位的核心，不应删除。必须保持：

- 设备只能通过固定工具调用；
- 设备必须先通过注册和类型校验；
- 离线设备不能执行控制；
- 命令必须包含有效的 request ID 和过期时间；
- 控制必须经过安全规则；
- 默认适配器仍为 simulated，联调时才显式使用 mqtt；
- 禁止把 GPIO、任意 Topic 或底层数据点暴露给大模型。

### 3. 路由和 LangGraph 路径

重点检查：

~~~text
financial_rag/rag_backend/app/multi_agent_system/routing/unified_router.py
financial_rag/rag_backend/app/langgraph/nodes.py
~~~

需要确认单房间家居的控制、状态、环境、模式和场景请求不会被默认导向动态 RAG 检索。若保留知识问答分支，必须与设备控制链路隔离，并且不能作为论文主线或设备执行依据；更简单的做法是移除家居业务默认 RAG 分支。

### 4. API 配置

重点检查：

~~~text
financial_rag/rag_backend/app/api/v1/endpoints/chat.py
financial_rag/rag_backend/app/api/v1/endpoints/multi_agent.py
~~~

处理 enable_rag、RAG 初始化和请求参数，避免 API 层继续默认打开家居 RAG。不要为了兼容历史配置而让运行时仍然实际检索。

## 五、论文方向应聚焦的内容

论文不需要证明 RAG 的效果，重点放在：

1. 单房间智能家居场景建模；
2. 自然语言到结构化控制意图的转换；
3. 固定工具调用协议和工具白名单；
4. 设备状态感知、状态验证和执行回执；
5. 注册设备、在线状态、命令 TTL、request ID 和安全规则；
6. 模拟设备闭环，以及后续 MQTT/STM32 联调方式；
7. 错误指令、越权设备、离线设备和过期命令的拒绝效果。

论文中可以明确说明：

> 本系统不采用动态知识检索作为设备控制决策机制，因为本研究场景中的设备集合、控制工具和安全约束均已固定。系统重点是验证大模型语义理解结果能否在确定性工具和安全边界约束下可靠执行。

## 六、修改边界

### 必须完成

- 关闭或移除单房间家居主链路中的运行时 RAG；
- 保证自然语言理解仍能路由到固定家居工具；
- 保证状态验证和安全控制仍然生效；
- 统一项目名称、README、架构文档和论文方向描述；
- 补充或更新测试，证明控制请求不依赖 RAG 也能完成。

### 不要做

- 不要扩展多房间、多租户或复杂家庭管理；
- 不要重新设计整个 Agent 框架；
- 不要删除 device_tools.py、device_service.py、safety_rules.py；
- 不要把固定规则改造成动态知识库；
- 不要让大模型直接生成 GPIO、MQTT Topic 或任意设备命令；
- 不要为了“清理 RAG”一次性删除所有通用 RAG 文件，先确认依赖关系；
- 不要修改真实硬件接线或接入 220V 市电。

## 七、验收标准

至少验证以下场景：

| 场景 | 预期结果 |
|---|---|
| “打开客厅灯”或等价单房间开灯请求 | 大模型识别意图后调用固定灯光工具并返回状态 |
| “关闭风扇” | 调用固定风扇工具，不能生成任意 Topic |
| 查询温湿度 | 通过设备服务读取当前状态，不通过知识库猜测 |
| 控制未注册设备 | 被拒绝 |
| 控制离线设备 | 被拒绝并返回原因 |
| 过期命令或重复 request ID | 被拒绝或按幂等规则处理 |
| 不明确或危险请求 | 不执行设备动作，要求澄清或返回安全拒绝 |
| RAG/向量服务不可用 | 家居固定工具主链路仍可运行，或明确快速失败，不能静默改变安全边界 |

修改后至少运行：

- 后端家居单元测试；
- git diff --check；
- 前端 npm run build。

## 八、给新对话的执行指令

请按以下顺序工作：

1. 阅读本交接文档、AGENTS.md、现有智能家居架构文档和 Git 状态；
2. 用代码搜索确认所有 RAG 运行时入口及其调用关系；
3. 先补充或调整测试，明确“无 RAG 仍能完成固定工具调用”的预期；
4. 最小范围修改主编排、路由和 API 配置，关闭家居运行时 RAG；
5. 更新 README、项目介绍、交接文档和论文方向描述；
6. 运行验收测试，检查是否破坏设备状态验证和安全控制；
7. 最后汇报：修改了哪些文件、哪些 RAG 代码仍保留为历史基座、测试结果以及尚未处理的风险。

如果发现某个 RAG 模块仍被其他非家居功能依赖，不要直接删除；将它与单房间家居运行路径隔离，并在最终报告中说明。
