# 智能家居远程控制开发文档

## 1. 文档目标

说明如何在不重写现有系统的情况下，让当前前后端软件远程控制 ESP32 硬件。

项目目标链路：

```text
Vue 前端 → FastAPI 后端 → Agent/RAG → 安全规则 → MQTT Broker → ESP32 → 灯/风扇
```

## 2. 当前项目能复用什么

当前 `financial_rag` 已经具备：

- Vue 对话前端；
- FastAPI 后端；
- LLM 调用；
- RAG 检索；
- LangGraph 多 Agent 流程；
- Agent 工具注册和调用；
- SSE 流式输出。

当前还没有：

- MQTT 服务；
- ESP32 固件；
- 智能家居设备工具；
- 设备状态同步；
- 远程访问和认证配置。

因此不需要从零开发软件，只需增加一层“智能家居设备适配器”。

## 3. 已有开源项目和可借鉴经验

### 3.1 proactive-home-agent

地址：<https://github.com/berkyalkn/proactive-home-agent>

这是与本项目最接近的参考项目，包含 ESP32、MQTT、FastAPI、LangGraph、ChromaDB、Ollama 和前端仪表盘。

重点参考：

- ESP32 传感器数据上传；
- MQTT 主题设计；
- 后端接收设备状态；
- Agent 调用设备动作；
- 本地部署和隐私处理。

不建议直接复制整个项目。当前项目已经有 RAG、Agent 和 Vue，不需要再替换整套架构。

### 3.2 agentic-iot-local-llm

地址：<https://github.com/aaryangupta/agentic-iot-local-llm>

这是一个较小的教育型原型，包含 ESP32、MQTT、Ollama、Python Agent、LED 控制和状态面板。

重点参考：

```text
观察 → 推理 → 执行 → 反馈
```

适合用来理解第一个可运行版本，不适合作为生产系统直接部署。

### 3.3 Home LLM

地址：<https://github.com/acon96/home-llm>

它主要通过 Home Assistant 让大模型控制家居设备。

重点参考：

- 设备能力如何抽象；
- 大模型如何调用固定工具；
- 如何避免大模型直接生成任意硬件指令；
- 设备状态如何返回给模型。

### 3.4 DotX Aero

地址：<https://github.com/kyoo-147/DotX_Aero>

包含语音、Ollama、MQTT、ESP32 和 Qdrant RAG，但项目已经停止维护。

只建议参考组合思路，不建议作为当前项目的核心依赖。

## 4. 推荐的远程控制架构

```text
手机/电脑浏览器
       ↓ HTTPS
Vue 前端
       ↓ HTTPS
远程 FastAPI 后端
       ↓ MQTT over TLS
公网 MQTT Broker
       ↓ MQTT over TLS
ESP32
       ↓
LED / 5V 风扇 / 传感器
```

### 重要原则

- 前端不直接连接 ESP32；
- 前端不直接连接 MQTT Broker；
- ESP32 主动向 MQTT Broker 建立出站连接；
- 不给 ESP32 做公网端口映射；
- 后端是 Agent 和硬件之间的唯一控制入口。

## 5. MQTT 主题契约

| 用途 | MQTT 主题 | 方向 |
|---|---|---|
| 灯光控制 | `home/bedroom/light/set` | 后端→ESP32 |
| 灯光状态 | `home/bedroom/light/state` | ESP32→后端 |
| 风扇控制 | `home/bedroom/fan/set` | 后端→ESP32 |
| 风扇状态 | `home/bedroom/fan/state` | ESP32→后端 |
| 传感器数据 | `home/bedroom/sensors` | ESP32→后端 |
| 设备在线状态 | `home/bedroom/status` | ESP32→后端 |

控制消息示例：

```json
{
  "request_id": "req-20260301-001",
  "device": "fan",
  "action": "set_state",
  "state": "on"
}
```

状态消息示例：

```json
{
  "request_id": "req-20260301-001",
  "device": "fan",
  "state": "on",
  "success": true
}
```

传感器消息示例：

```json
{
  "temperature": 26.4,
  "humidity": 61,
  "light": 420,
  "person": true,
  "timestamp": 1710000000
}
```

## 6. 后端开发改造

### 6.1 新增 MQTT 服务

建议新增：

```text
financial_rag/rag_backend/app/services/mqtt_service.py
```

负责：

- 连接 MQTT Broker；
- 发布设备控制消息；
- 订阅设备状态；
- 断线重连；
- 超时处理；
- 记录 MQTT 错误。

连接配置使用环境变量：

```text
MQTT_BROKER_HOST
MQTT_BROKER_PORT
MQTT_USERNAME
MQTT_PASSWORD
MQTT_CA_CERT
MQTT_CLIENT_ID
```

不要把密码、Token 或证书私钥写入代码和 Git。

### 6.2 新增智能家居工具

建议新增：

```text
financial_rag/rag_backend/app/tools/smart_home_tools.py
```

第一版只实现：

```text
read_sensors()
get_device_status()
set_light(state: "on" | "off")
set_fan(state: "on" | "off")
```

工具参数必须是固定枚举，不允许模型传入任意 MQTT Topic 或任意 GPIO 编号。

### 6.3 注册工具

复用现有：

```text
financial_rag/rag_backend/app/agent_framework/tools/agent_tool_registry.py
```

只给智能家居专家开放设备工具：

- 环境感知专家：`read_sensors`、`get_device_status`；
- 设备控制专家：`set_light`、`set_fan`、`get_device_status`；
- 舒适度专家：只读传感器和知识库，不直接控制设备；
- 总管家：负责分派，不直接绕过安全规则。

### 6.4 安全规则

设备工具执行前检查：

```text
设备是否存在
动作是否支持
参数是否在白名单
设备是否在线
是否超过超时时间
是否需要人工确认
```

执行顺序：

```text
Agent 工具调用
→ 参数校验
→ 设备能力校验
→ 安全规则
→ MQTT 发布
→ 等待状态反馈
→ 返回结果
```

## 7. ESP32 开发内容

ESP32 使用 Arduino IDE 烧录程序，实现：

1. 连接 Wi-Fi；
2. 校准系统时间；
3. 使用 TLS 连接 MQTT；
4. 订阅灯和风扇控制主题；
5. 读取 DHT22、BH1750 和 PIR；
6. 控制 LED 和 5V 小风扇；
7. 发布传感器数据；
8. 发布在线、离线和执行状态。

推荐使用设备遗嘱（LWT）：

```text
连接断开 → 发布 offline
成功上线 → 发布 online
```

## 8. 远程部署步骤

### 第一步：本地模拟

先不接 ESP32，使用模拟设备完成：

```text
Vue → FastAPI → Agent → 模拟设备工具 → 模拟状态
```

### 第二步：局域网 MQTT

在电脑上运行 Mosquitto 或其他 Broker：

```text
FastAPI ↔ MQTT Broker ↔ ESP32
```

确认灯、风扇和传感器闭环正常。

### 第三步：云端 MQTT

将 Broker 部署到云服务器或使用托管 MQTT 服务：

```text
ESP32 → 公网 MQTT Broker
FastAPI → 公网 MQTT Broker
```

两者都使用 TLS 和账号认证。

### 第四步：远程访问后端

将 FastAPI 部署为 HTTPS 服务，Vue 前端只访问后端 API。

最终：

```text
手机 4G/5G → HTTPS → FastAPI → MQTT → ESP32
```

## 9. 已有人报告过的相关问题

下面不是凭空假设，而是公开项目 Issue 中出现过的问题。它们应当直接转化为本项目的开发测试项。

| 来源 Issue | 已报告现象 | 本项目的应对测试 |
|---|---|---|
| [PubSubClient #1085](https://github.com/knolleary/pubsubclient/issues/1085) | ESP32 每 1～4 秒反复重连；重复使用 MQTT Client ID 时，Broker 会踢掉旧连接 | 每台设备使用唯一 Client ID；模拟断网并观察是否进入重连循环 |
| [PubSubClient #951](https://github.com/knolleary/pubsubclient/issues/951) | Wi-Fi 仍连接但公网已断开，`connected()` 仍可能返回 true；`publish()` 或 `loop()` 可能阻塞并触发看门狗 | 分离测试 Wi-Fi 断开、Broker 断开和公网断开；所有发布都设置超时 |
| [ESP-MQTT #126](https://github.com/espressif/esp-mqtt/issues/126) | 写超时后重连失败，并出现堆内存持续增长 | 连续断网/恢复 100 次，记录堆内存和重连耗时；不要同时手动重连和自动重连 |
| [ESP-MQTT #133](https://github.com/espressif/esp-mqtt/issues/133) | Wi-Fi 或 Broker 恢复后，自动重连不一定成功 | 测试 Broker 重启和路由器重启，确认设备最终恢复在线 |
| [PubSubClient #1017](https://github.com/knolleary/pubsubclient/issues/1017) | MQTT 缓冲区存在大小限制，大消息可能发布失败 | 控制消息只保留小 JSON；禁止通过 MQTT 传图片、PDF 等大文件 |

这些 Issue 是用户环境相关的公开报告，不代表每个版本都会复现，但非常适合作为回归测试清单。

## 10. 论坛中尚未完全解决的问题

以下是 Arduino Forum 等公开讨论中，开发者曾经遇到、但没有形成统一根因或通用修复方案的问题。它们适合列为本项目的重点风险，不应直接当成必然 Bug。

| 论坛讨论 | 开发者遇到的问题 | 当前能得到的结论 |
|---|---|---|
| [MQTT stops publishing after a while](https://forum.arduino.cc/t/mqtt-stops-publishing-after-a-while/1215918) | 设备运行一段时间后停止发布，重启后恢复 | 可能与 Keep Alive、网络轮询或库行为有关；有人报告调整 Keep Alive 后改善，但不是通用解法 |
| [Sketch stops sending MQTT messages after many hours](https://forum.arduino.cc/t/sketch-stops-sending-mqtt-messages-after-many-hours/1344155) | 运行数小时后不再发送 MQTT，具体停止时间不稳定 | 讨论中涉及 Wi-Fi、MQTT 重连、内存碎片和供电，未形成单一确定根因 |
| [ESP32 running Arduino and MQTT keeps hanging](https://forum.arduino.cc/t/esp32-running-arduino-and-mqtt-keeps-hanging/1316508) | MQTT 或重连过程卡死，可能触发看门狗 | 阻塞式重连是高风险点，但不同硬件和库版本可能表现不同 |
| [ESP32 W5500 MQTT reconnect problem](https://forum.arduino.cc/t/esp32-w5500-mqtt-reconnect-problem/870557) | 以太网或 MQTT 断开后无法稳定恢复 | 需要分别排查 W5500、网络链路、Broker 和 MQTT 客户端，不能只修改重连函数 |

### 这些问题如何处理

不要一开始用 `ESP.restart()` 掩盖问题。开发时必须记录：

```text
Wi-Fi 状态、MQTT 状态、Broker 错误码、TLS 错误、剩余堆内存、重启原因、最后一次成功发布时间
```

如果最终仍无法复现或彻底解决，应在论文中如实写成“异常恢复与容错设计”，并说明：

- 使用非阻塞重连和指数退避；
- 设置发布和状态确认超时；
- 使用 LWT 标记设备离线；
- 多次失败后才执行受控重启；
- 保存错误日志用于定位，而不是宣称已消除所有网络异常。

## 11. 已知经验和常见 Bug

### Bug 1：TLS 证书验证失败

常见原因：

- ESP32 没有配置 CA 证书；
- 系统时间错误；
- 证书域名与 Broker 地址不一致；
- 证书已经过期。

处理方式：

- ESP32 启动后先用 SNTP 同步时间；
- 使用正确的 CA 证书；
- 先记录详细 TLS 错误，再判断是否是网络问题。

参考：

<https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-reference/protocols/esp_tls.html>

### Bug 2：ESP32 连接几秒后掉线

常见原因：

- 没有频繁调用 MQTT `loop()`；
- 主循环中使用了长时间阻塞的 `delay()`；
- 传感器读取或重连代码阻塞太久；
- Keep Alive 设置不合理。

处理方式：

- MQTT 循环保持高频运行；
- 传感器采集使用定时器，不使用长阻塞；
- 重连使用递增等待，不要死循环重连。

### Bug 3：ESP32 重连后突然执行旧命令

原因：

- 把一次性控制命令设置成 retained 消息；
- ESP32 重新订阅后收到历史命令。

处理方式：

- `set` 控制命令默认不使用 retained；
- retained 只用于当前状态和在线状态；
- 控制命令增加 `request_id` 和过期时间。

### Bug 4：命令被执行两次

原因：

MQTT QoS 1/2 可能发生重复投递，网络重连时更容易出现。

处理方式：

- 控制操作设计为幂等操作；
- ESP32 记录最近处理过的 `request_id`；
- “打开风扇”可以重复执行，但“增加亮度 10%”需要序列号或去重。

参考：

<https://docs.espressif.com/projects/esp-idf/en/v5.5.4/esp32/api-reference/protocols/mqtt.html>

### Bug 5：后端显示成功，但硬件没有动作

常见原因：

- 后端只确认 MQTT 发布成功，没有等待 ESP32 状态反馈；
- Topic 拼写不一致；
- ESP32 没有订阅正确主题；
- GPIO 接线错误；
- 风扇供电不足。

处理方式：

```text
发布成功 ≠ 设备执行成功
```

后端应等待对应的 `state` 消息，超时后显示“未收到设备确认”。

### Bug 6：设备状态显示不准确

常见原因：

- 前端只根据按钮点击修改状态；
- 没有处理设备离线；
- 没有区分“命令发送中”和“设备已执行”。

建议状态至少分为：

```text
在线、离线、执行中、已执行、执行失败、等待确认
```

### Bug 7：远程连接不安全

错误做法：

- 给 ESP32 做端口映射；
- 对公网开放 MQTT `1883`；
- 开启匿名 MQTT；
- 把 MQTT 密码写入前端；
- 让前端直接发布 MQTT 命令。

正确做法：

```text
ESP32 出站连接 Broker
Broker 使用 TLS
后端保存密钥
前端只访问 HTTPS 后端
Broker 配置最小权限 ACL
```

Mosquitto ACL 参考：

<https://www.mosquitto.org/documentation/plugins/acl-file/>

### Bug 8：风扇启动导致 ESP32 重启

常见原因：

- 风扇启动电流使电压下降；
- ESP32 和风扇共用不稳定电源；
- 没有共地；
- 继电器或 MOSFET 接线错误。

处理方式：

- 使用独立稳定的 5V 风扇电源；
- ESP32 与控制模块共地；
- 第一版只使用 5V 小风扇；
- 不接 220V 市电。

## 12. 最小验收标准

### 软件验收

- 用户输入“打开风扇”后，Agent 能调用 `set_fan`；
- 非法设备或非法状态会被后端拦截；
- 后端能够发布 MQTT 控制消息；
- 后端能收到 ESP32 状态反馈；
- 前端能显示成功、失败和超时；
- ESP32 断网后能够自动重连。

### 远程验收

- ESP32 不暴露公网端口；
- MQTT 使用 TLS；
- 前端使用 HTTPS；
- 外部网络可以发送控制请求；
- 设备离线时不会显示虚假的“执行成功”。

### 答辩演示验收

```text
手机输入“请打开桌面风扇”
→ Agent 识别设备控制
→ 安全规则检查
→ MQTT 下发命令
→ ESP32 启动风扇
→ ESP32 返回状态
→ 前端显示“风扇已开启”
```

## 13. 推荐结论

不要从零重写前后端，也不要先做复杂的 Home Assistant 平台。

第一版采用：

```text
现有 financial_rag
+ 一个 MQTT 服务
+ 四个固定设备工具
+ 一个 ESP32 Arduino 固件
+ LED 和 5V 小风扇
```

先在局域网跑通，再把 MQTT Broker 和 FastAPI 放到云端，最后实现真正的远程控制。
