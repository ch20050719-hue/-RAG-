## 5. 通信方式与关键定义

本项目采用机智云独立 MCU 方案：STM32 经 USART2 与 ESP8266 交换机智云串口协议数据，模组上的兼容 GAgent 固件负责连接云端。当前源码串口配置为 PA2/PA3、9600、8N1；实物模块固件和接线仍需按已确认硬件核实。

设备与机智云的网络通信采用 MQTT。新建机智云产品不需要另外搭建 MQTT Broker，也不需要“生成一个 MQTT”。要更新并核对的是产品身份、数据点协议、设备注册和 APP 绑定。Product Key 是产品标识，不能把同一 ESP8266 的旧产品绑定当成新产品接入成功。

| 数据点 | 定义与执行行为 |
|---|---|
| `System_Mode` | 0 手动、1 自动；独立灯／风扇／窗户控制先使用手动模式验证 |
| `Door_Target` | 0 未下发，不动作；1 开门；2 关门；回报最近接受的目标 |
| `Home_Scene` | 0 正常；1 睡眠；2 离家；手机端使用一个选择框 |

睡眠：切到手动、开风扇、关灯、下发关门目标。离家：切到手动、关风扇、关灯、下发关门目标。正常：仅清除场景标记，不恢复此前设备状态，也不自动改为自动模式。执行独立 APP 灯／风扇／窗户操作时，手动模式下清除场景标记；独立开门／关门命令也会清除场景标记。

没有位置传感器，门目标不能解释为门体已到位或已锁好。

## 7. 已知问题与证据边界

### 7.1 定时全量上报可能漏触发

`gizwits_protocol.c` 的 `gizDevReportPolicy()` 当前使用：

```c
if ((0 == (timeNow % 600000)) && (lastRepTime != timeNow))
```

这要求主循环恰好在 600000 毫秒的整数倍执行到此处。主循环含 `Delay_ms(120)`，可能越过该时刻，从而漏掉计划的全量上报。这是源码路径确认的风险，尚未做动态复现或修复。

下一次修复应按时间差是否达到周期判断，并测试跨过整点、计时回绕及避免连续重复上报。不要只改注释或扩大延时。

`REPORT_TIME_MAX=6000` 用于限制传感器变化上报的间隔，不代表每 6 秒全量上传。该计时也会被其他状态变化上报更新，因此不能保证传感器变化每 6 秒必定上传。

另有待修复的状态同步风险：传感器变化在未到 6 秒时不设置报告标志，但灯或门等即时变化可触发同轮上报；随后代码把整个 `currentData` 复制到 `gizLastDataPoint`，也把本轮未上报的传感器数值记成已报告基线。如果此后读数稳定，该变化可能不会再触发变化上报。后续测试需覆盖“传感器变化与设备操作同时发生”的情况，不能仅验证传感器单独变化。

### 7.2 代码上报不等于云端收到

主循环调用链已存在，但 STM32 串口发送成功只能证明数据交给模组的代码路径。模组上线、新产品归属、云端接收和 APP 展示仍需分段验证。

`WIFI_CON_M2M`、`WIFI_DISCON_M2M` 的产品层处理目前为空，不能依靠该处理函数中的提示判断连接成功。应查看设备在线状态、模组日志和实际云端上报记录。

### 7.3 采集失败可能继续显示旧值

温湿度和 ADC 无效时，`userHandle()` 保留此前的数据点数值。当前物模型没有采集有效位，APP 无法仅凭数值判断是否为旧读数。不要将不变的 APP 数值直接解释为传感器持续采集成功。

## 8. 下一步执行顺序

1. 先核对当前板卡烧录的固件版本、模组固件和新产品归属。用户已确认 C6 能跑通，但该确认没有对应本次新协议的逐项云端验收记录。
2. 修复并测试定时全量上报问题；重新运行相关逻辑测试、Keil 编译，记录实际限制，不用编译成功代替断言通过。
3. 使用工作工程生成的固件进行板卡联调；模组入网后，在新产品“设备管理”中核对 MAC、设备 ID 和在线状态。仍显示旧产品时先查产品信息和绑定。
4. 打开实物设备的实时调试，验证上报。不要用虚拟设备的日志代替实物证据。
5. 再验证灯、风扇、窗户、门目标、场景、阈值和传感器；记录下发与回报，并做重连验证。

### 云端接收记录怎么查看

1. 登录机智云开发者中心，进入新产品“STM32智能家居”。
2. 点击左侧“设备管理”，找到当前实物设备，核对 MAC 和在线状态。
3. 打开该设备的“实时调试”；若当前界面命名不同，在设备详情中查找通信日志入口。切到 JSON 查看字段，必要时保留原始数据辅助排查。
4. 先打开日志，再在 APP 中切到手动模式，开灯、关灯。观察对应时间是否出现设备回报的 `Light` 新值。
5. 区分方向：`app2dev` 是指令下发，`dev2app` 是设备到应用方向；关注上报字段与变化，不只看“在线”或下发成功。
6. 记录时间、方向、字段和值。必要时将手机切换到移动数据，验证远程链路，并以开发者中心日志作为云端接收证据。

如果列表为空，尚不能验证该产品实物上报；先排查新产品身份、模组入网及设备注册。APP 上显示数据本身可能来自局域网链路，不能单独作为云端接收证据。

## 10. 容易混淆的结论

| 容易误判 | 正确结论 |
|---|---|
| 新建产品就要生成一个 MQTT | 继续使用机智云通信服务，核对新产品身份、协议与绑定 |
| 新包包含门控和场景，说明实物已支持 | 固件已接入，实物和 APP 验收仍待记录 |
| COUNT_BIT 改为 2 就能修复云端的错误枚举 | 云端枚举必须独立定义并重新生成 SDK，再核对本地协议 |
| 编译通过，说明测试通过 | Keil 构建、测试断言、板卡运行、云端接收是四类证据 |
| 用户说 C6 能跑通，说明新产品所有功能通过 | 硬件运行确认不能代替新协议与云端的逐项验收 |
| 每 6 秒上传全部数据 | 6 秒是传感器变化上报限制；定时全量条件写的是 10 分钟且可能漏触发 |
| APP 数值更新或设备在线，说明云端已收到 | 对照实物设备的云端上报日志和字段变化 |
| 门目标为关门，说明门已锁好 | 只表示已接受关门目标，没有位置反馈 |


新产品固件出现异常时，先保留云端日志与板卡复现步骤，再依据用户确认的可用固件版本回退；不直接覆盖整个工作目录，不修改只读基线。旧生成包枚举异常，不能作为可用的新产品协议回滚版本。云端数据点和本地固件必须匹配，回退其中一侧后应重新核对另一侧。

实物验收按以下字段记录，不填入凭据：

| 字段 | 应记录的内容 |
|---|---|
| 时间 | 操作与上报记录时间 |
| 固件 | HEX 路径与 SHA256、板卡 C6 配置 |
| 模组 | 实际型号、GAgent 版本、接线及配网方式 |
| 产品／设备 | 产品名、物模型版本、脱敏设备标识 |
| 操作 | 手动开关、门目标、场景、读数变化或重连 |
| 云端证据 | 上报方向、字段和值，区分下发与回报 |
| 实物结果 | 实际动作，区分目标状态与位置反馈 |
| 结论 | 通过／失败／未验证，以及复现条件 |
