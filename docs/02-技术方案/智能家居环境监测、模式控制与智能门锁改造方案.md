## 1. 项目定位与改造目标

### 1.1 项目定位

系统仅面向一个房间进行智能家居演示。核心闭环为：

~~~text
传感器采集
  → ESP32/MQTT 上报
  → 后端数据校验
  → 环境历史记录
  → 阈值判断与故障诊断
  → 风扇联动或报警通知
  → 前端曲线、状态和报警展示
  → 主 Agent 调度子 Agent 控制设备
~~~

### 1.2 改造目标

首版只完成以下能力：

1. 监测一个房间的温度、湿度和 CO₂；
2. 实时展示环境数据和历史曲线；
3. 根据环境值自动控制低压 5V 风扇；
4. 支持睡眠模式和离家模式；
5. 识别真实报警、疑似误报、传感器故障和门锁故障；
6. 支持远程解锁、远程上锁和解除室内反锁；
7. 由主 Agent 调度环境检测子 Agent 和设备控制子 Agent；
8. 保留模拟设备模式，便于无硬件演示和自动化测试。

## 2. 范围、设备与安全边界

### 2.1 单房间范围

| 项目 | 首版配置 |
|---|---|
| 房间数量 | 1 个 |
| 默认房间 | 书房 `study` |
| 环境传感器 | 温度、湿度、CO₂ |
| 执行器 | 低压 LED、5V 风扇 |
| 门禁设备 | 具备状态反馈的智能门锁和门磁 |
| 通信方式 | 模拟适配器或 MQTT |
| 数据展示 | 当前值、历史曲线、报警状态 |

### 2.2 不纳入首版

- 多房间和多家庭管理；
- 摄像头、人脸识别和身份推断；
- 燃气、加热、电热水器和 220V 家电；
- 任意品牌设备自动发现；
- 任意 MQTT Topic 或 GPIO 控制；
- 无人状态下自动打开实体房门；
- 复杂的物业门禁、消防联动和公网远程运维。

### 2.3 门锁安全边界

智能门锁是高风险设备，必须与 LED、风扇使用独立的门锁模型、权限校验和审计记录。

门锁必须满足：

- 室内可以不依赖网络、手机或服务器直接开门；
- 能返回门开/关状态；
- 能返回锁定、解锁和反锁状态；
- 能返回低电量、离线、卡死和异常状态；
- 控制接口支持身份认证和权限区分；
- 支持失败安全策略和人工现场处理；
- 设备厂商明确支持远程控制和本地应急开门。

远程解锁默认只表示“解除锁定”，不表示门已经自动打开。若要求门自动开启，还需要电动开门机构，不属于本首版范围。

### 3.1 控制原则

~~~text
用户/Agent 请求
  → 服务端身份与权限校验
  → 设备注册与能力校验
  → 在线状态校验
  → 门磁/模式/安全状态校验
  → 固定动作白名单
  → 适配器执行
  → 等待设备 ack
  → 更新状态和审计
~~~

MQTT 发布成功不等于设备执行成功，只有收到匹配设备和 `request_id` 的 ack 后，前端才显示成功。

## 4. 环境监测与自动联动

### 4.1 传感器注册

默认传感器：

| sensor_id | 类型 | 单位 |
|---|---|---|
| `room_temp` | 温度 | ℃ |
| `room_humidity` | 湿度 | % |
| `room_co2` | 二氧化碳 | ppm |

每条读数必须包含：

~~~text
sensor_id
room
kind
value
unit
recorded_at
online
source
~~~

### 4.2 阈值配置

以下为首版演示规则，不应在论文中表述为适用于所有家庭的绝对安全标准。

| 指标 | 正常范围 | 预警条件 | 危险条件 |
|---|---|---|---|
| 温度 | 18～28℃ | <18℃ 或 >28℃ | <10℃ 或 ≥35℃ |
| 湿度 | 30%～60% | <30% 或 >60% | <20% 或 ≥80% |
| CO₂ | <1000 ppm | 1000～1499 ppm | ≥1500 ppm |

EPA 资料将超过 1000 ppm 的 CO₂ 视为可能存在通风问题；室内相对湿度通常建议维持在 30%～50% 并低于 60%。ASHRAE 提醒，舒适度还与温度、空气流速、衣着和活动量有关，因此项目阈值需要保持可配置。

### 4.3 自动联动动作

| 条件 | 正常模式 | 睡眠模式 | 离家模式 |
|---|---|---|---|
| 高温预警 | 开启风扇 | 开启风扇 | 只报警，默认不启动设备 |
| 高湿预警 | 开启风扇 | 开启风扇 | 只报警，默认不启动设备 |
| CO₂ 预警 | 开启风扇并提示通风 | 开启风扇并提示通风 | 只报警，默认不启动设备 |
| 温度危险 | 开启风扇并报警 | 开启风扇并报警 | 报警并提示返回处理 |
| 湿度危险 | 开启风扇并报警 | 开启风扇并报警 | 报警并提示返回处理 |
| CO₂ 危险 | 开启风扇并报警 | 开启风扇并报警 | 报警并提示返回处理 |
| 低温/低湿 | 报警，不开风扇 | 报警，不开风扇 | 报警，不开风扇 |
| 传感器数据无效 | 不执行自动控制 | 不执行自动控制 | 不执行自动控制 |

风扇仅用于辅助空气流动，不能将其描述为足以解决极端高温或 CO₂ 风险的唯一措施。

## 5. 睡眠模式与离家模式

### 5.1 睡眠模式

~~~text
请求进入睡眠模式
  → 关闭 LED
  → 检查门磁是否 closed
  → 门已关闭：执行室内反锁
  → 等待 deadbolt ack
  → 确认反锁状态
  → 启动睡眠环境规则
~~~

睡眠模式规则：

- LED 强制关闭；
- 温度达到 28℃、湿度达到 70% 或 CO₂ 达到 1000 ppm 时开启风扇；
- 温度低于 26℃、湿度低于 65% 且 CO₂ 低于 1000 ppm 时关闭风扇；
- 环境危险时保持报警并继续执行允许的风扇动作；
- 门没有关闭时不得反锁，模式进入 `sleep_blocked` 或 `sleep_pending`；
- 告警确认后，用户可通过二次认证解除反锁。

### 5.2 离家模式

~~~text
请求进入离家模式
  → 关闭 LED 和风扇
  → 检查门磁是否 closed
  → 门已关闭：执行普通上锁
  → 等待 lock ack
  → 确认 locked 状态
  → 启动离家监测规则
~~~

离家模式规则：

- LED 和风扇默认关闭；
- 温度、湿度和 CO₂ 仍然持续监测；
- 环境异常时发送报警，但默认不自动开启风扇；
- 门未关闭时不执行上锁，并提示用户处理；
- 门锁离线或没有 ack 时，离家模式不得显示为完成；
- 离家模式重点是节能和门锁状态确认，睡眠模式重点是有人使用时的舒适度调节。

### 5.3 模式状态

~~~text
normal
sleep_pending
sleep_active
sleep_blocked
away_pending
away_active
away_blocked
~~~

模式切换成功的判断条件必须包括设备 ack，而不能只判断 API 请求是否返回 200。

## 6. 报警、误报与故障诊断

### 6.1 报警状态

~~~text
normal          正常
suspected       疑似异常
active          已确认报警
sensor_fault    传感器故障
recovered       报警已恢复
~~~

### 6.2 真实报警确认

建议采用以下判断顺序：

1. 校验 JSON 格式、传感器 ID、单位和数值类型；
2. 检查传感器是否在线；
3. 检查数据时间是否新鲜；
4. 检查读数是否在传感器允许的物理范围内；
5. 要求连续 2～3 次超过阈值；
6. 检查变化速度是否合理；
7. 结合当前模式和风扇执行结果形成诊断证据；
8. 满足条件后升级为 `active`。

### 6.3 误报判断依据

| 现象 | 系统判断 |
|---|---|
| 只出现一次异常尖峰，下一次恢复 | `suspected`，不立即确认 |
| 数据连续缺失或超过 30 秒未更新 | `sensor_fault` |
| 数值超出传感器合理范围 | `sensor_fault` |
| 短时间内出现不可能的大幅变化 | `suspected` 或传感器故障 |
| 连续多次越过阈值且趋势合理 | `active` |
| 开启风扇后 CO₂ 逐步下降 | 支持真实环境异常判断 |
| 开启风扇后数值没有改善 | “环境未改善”，不能直接认定为误报 |
| 连续多次恢复正常 | `recovered` |

误报判断不是简单地删除报警，而是先进入“疑似异常”，保留原始读数和判断依据，便于后续审计。

### 6.4 故障来源定位

每条报警必须指出：

~~~text
房间：书房
传感器：room_co2
指标：二氧化碳
当前值：1680 ppm
危险阈值：1500 ppm
连续异常次数：3
数据来源：MQTT
最后更新时间：具体时间
~~~

系统需要区分：

- 环境确实异常；
- 传感器数据错误；
- 传感器离线；
- MQTT 传输异常；
- 风扇执行失败；
- 门锁执行失败。

## 7. 智能门锁接入与控制流程

### 7.1 门锁状态

~~~text
door_state: open / closed
lock_state: locked / unlocked
deadbolt_state: engaged / released
online: true / false
battery_state: normal / low
jammed: true / false
tampered: true / false
~~~

### 7.2 远程解锁

~~~text
用户点击远程解锁
  → 身份和房间权限校验
  → 二次认证
  → 生成短有效期 request_id
  → 调用 unlock_door
  → 等待门锁 ack
  → 显示门锁已解除
  → 等待 door_state=open
~~~

如果只有解锁 ack，没有门磁 `open` 事件，系统只能报告“门锁已解除”，不能报告“人员已经进门”。

### 7.3 来访者进门后远程上锁

建议通过以下事件序列识别一次完整进门过程：

~~~text
远程解锁成功
  → door_state=open
  → door_state=closed
  → 用户点击远程上锁
  → 检查门已关闭
  → 调用 lock_door
  → 等待 locked ack
~~~

如果门仍然打开，必须拒绝上锁并提示：

~~~text
房门仍处于打开状态，暂不能上锁。
~~~

如果需要自动上锁，可以在门关闭后等待固定时间，例如 60 秒，但必须作为单独的可配置策略，不能默认强制开启。

### 7.4 睡眠模式反锁

~~~text
进入睡眠模式
  → 检查 door_state=closed
  → 调用 engage_deadbolt
  → 等待 deadbolt_state=engaged
  → 确认睡眠模式完成
~~~

门未关闭、门锁离线、低电量、卡死或 ack 超时时，不得显示“已反锁”。

### 7.5 告警后解除反锁

~~~text
环境报警确认
  → 发送报警通知
  → 用户点击解除反锁
  → 二次认证
  → 显示报警来源和门锁状态
  → 用户确认
  → 调用 release_deadbolt
  → 等待 deadbolt_state=released
~~~

解除反锁不等于自动开门。首版只解除门锁反锁状态，不自动驱动门扇打开。

疑似误报、传感器故障和门锁故障不能自动执行门锁动作。用户仍可以在完成二次认证后手动发起操作，但系统必须明确显示风险和当前故障。

## 8. 主 Agent 与子 Agent 调用路线

### 8.1 角色结构

~~~text
智能家居主 Agent
├── 环境检测子 Agent
└── 设备控制子 Agent
~~~

### 8.2 主 Agent

职责：

- 理解用户自然语言；
- 判断环境查询、模式切换、设备控制或门锁控制；
- 调度对应子 Agent；
- 汇总工具结果；
- 只根据设备 ack 报告成功。

### 8.3 环境检测子 Agent

允许调用：

~~~text
read_home_environment
get_environment_history
get_home_alerts
get_device_status
~~~

禁止调用：

~~~text
unlock_door
lock_door
engage_deadbolt
release_deadbolt
set_light_state
set_fan_state
~~~

### 8.4 设备控制子 Agent

允许调用：

~~~text
get_device_status
set_light_state
set_fan_state
run_home_mode
get_door_status
unlock_door
lock_door
engage_deadbolt
release_deadbolt
~~~

门锁动作必须额外经过高风险权限和二次认证检查。门锁工具不得接收任意 Topic、GPIO、厂家命令或用户拼接的底层参数。

## 9. MQTT 与设备数据契约

### 9.1 Topic 规划

~~~text
home/v1/study/desk_node/telemetry
home/v1/study/desk_light/state/set
home/v1/study/desk_light/state/ack
home/v1/study/desk_fan/state/set
home/v1/study/desk_fan/state/ack
home/v1/study/door_lock/state/set
home/v1/study/door_lock/state/ack
home/v1/study/door_sensor/state
home/v1/study/availability
~~~

模型和前端不直接接触这些底层 Topic，Topic 只在 MQTT 适配器和设备联调文档中出现。

### 9.2 环境遥测示例

~~~json
{
  "device_id": "desk_node",
  "room": "study",
  "sensors": {
    "room_temp": 26.5,
    "room_humidity": 48.0,
    "room_co2": 820
  },
  "recorded_at": "2026-09-16T12:00:00Z"
}
~~~

### 9.3 门锁 ack 示例

~~~json
{
  "request_id": "uuid",
  "device_id": "door_lock",
  "accepted": true,
  "door_state": "closed",
  "lock_state": "locked",
  "deadbolt_state": "engaged",
  "battery_state": "normal",
  "message": "door lock acknowledged"
}
~~~

MQTT 控制使用 QoS 1、结构化 JSON、过期时间和 `request_id` 幂等。QoS 1 可能造成重复投递，设备端和后端都必须能够安全处理重复请求。

### 10.1 环境接口

~~~

### 10.2 模式接口

~~~text

~~~

模式请求：

~~~json
{
  "mode": "sleep"
}
~~~

允许值：

~~~text
normal
sleep
away
~~~

### 10.3 门锁接口

~~~text
GET  /api/v1/home/door/status
POST /api/v1/home/door/unlock
POST /api/v1/home/door/lock
POST /api/v1/home/door/deadbolt/engage
POST /api/v1/home/door/deadbolt/release
~~~

门锁操作返回值必须包含：

~~~text
accepted
request_id
door_state
lock_state
deadbolt_state
message
blocked_reason
acknowledged_at
~~~

### 10.4 审计字段

每次门锁或设备操作至少记录：

~~~text
interaction_id
request_id
user_id
room
device_id
action
mode
authorization_result
second_factor_result
adapter
ack_result
created_at
~~~

日志中不得保存密码、令牌、门锁 PIN 或 MQTT 密码。

## 16. 已知限制与实施前确认项

### 16.1 已知限制

- 现有项目默认设备范围是低压 LED 和 5V 风扇，智能门锁属于新增高风险设备；
- 普通智能锁的远程解锁不一定能够物理开门；
- 没有门磁就无法可靠判断门是否关闭；
- 没有真实推送服务时，站内通知不能等同于手机离线通知；
- 单房间演示不代表可以直接用于真实住宅门禁；
- 进门事件只能依据门锁和门磁状态，不能判断来访者身份；
- 内存历史缓存重启后可能丢失数据，持久化存储可作为后续扩展。

### 16.2 真实实施前必须确认

1. 智能门锁具体品牌和型号；
2. 是否支持远程解锁、普通上锁和室内反锁三个独立状态；
3. 是否提供受控本地 API、MQTT 或官方网关；
4. 是否有配套门磁；
5. 是否支持低电量、卡死和离线状态上报；
6. 报警通知渠道是站内通知、浏览器推送、手机 App、邮件还是其他渠道；
7. CO₂ 传感器具体型号；
8. 真实门锁联调是否只做实验室演示，不接入实际住宅门。
